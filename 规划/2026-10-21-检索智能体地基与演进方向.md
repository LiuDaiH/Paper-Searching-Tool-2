# 检索智能体地基与演进方向

> 2026-10-21 记录。长期参考：本文只定义检索智能体的**地基**——目标形态、状态/动作/Trace/评测/数据分层，以及演进顺序。具体模型架构、参数量和训练超参后置，另行成文。

## 0. 决策摘要

| 事项 | 决定 |
|---|---|
| 目标 | 本地语料上的可靠研究助手，不追求开放世界通用 LLM |
| 智能体形态 | 有边界的编排式单 controller + 专用工具 |
| 不采用 | 多智能体 swarm、自由 ReAct 主循环、端到端 RL 从零训练 |
| 第一优先级 | **先 Trace 观察，再修 L2 覆盖与工具成熟度；工具成熟后才冻结 ToolSpec/Controller** |
| 策略演进 | 当前 heuristic 作为 baseline；后续 policy 可替换 |
| 动作分层 | primitive tools + macro skills；宏动作在 Trace 中展开 |
| 工具演进 | 先过工具成熟度验收，再冻结接口/观测契约；版本化 + 回放 |
| 控制回路 | 工具成熟后用 LLM 直接调工具做冷启动；目标由专用 agent 主导检索控制 |
| 迁移路线 | 固定 heuristic baseline → 工具成熟 → ToolSpec/registry → LLM direct → 专用 agent |
| `scope` 归属 | 前端解析用户明确范围；后端校验并在候选层过滤；年份/会议约束不进入语义 coverage |
| 模型选型 | 后置；先积累 Trace 和分类型评测 |
| 对外契约 | 不改既有语义；新增字段只做 additive |

## 1. 背景与判断

项目最初的设想是一个 learned retrieval controller：问题 + 语料表示 → 检索动作 → LLM 生成答案。

当前实现更接近 LLM 驱动的 RAG pipeline：

```text
parse_query
  → hybrid 检索 / 子聚类
  → 簇命名
  → 带引用回答
  → 引用校验
```

这不是方向错了，而是当前工作主要完成了**工具层和环境层**：

- 语料、向量、BM25、hybrid 检索已经可用；
- 子聚类、证据门、引用校验、评测集已经具备；
- `AskResponse.meta` 已有 `plan / retrieval / evidence / decision` 的摘要；
- `usage.stages` 已能记录阶段起止。

缺的是显式的 **State / Action / Trace / Outcome**。如果继续把 query 越拆越细，只是在用 query patch 修表示、检索和选择问题，边际收益会越来越低。

目标不是“像通用 LLM”，而是“在本地 22,747 篇语料上可靠、可引用、可评测的研究助手”。

## 2. 目标智能体形态

采用**有边界的编排式单智能体**：

```text
Planner（QueryPlan）
  → Controller（显式状态机）
  → Tools（检索 / 聚类 / 取论文 / 关系）
  → Evidence Gate
  → Answer
  → Verify
  → 最多一次 repair
  → Trace
```

原则：

- 单 controller，多工具；工具不藏策略；
- 不做多智能体 swarm，不做自由 ReAct 主循环；
- 最多 1 次扩展、1 次 repair；
- LLM 只负责需要判断的节点，机械判断交给规则；
- 多智能体只在未来多源、并行研究场景再考虑。

## 3. 地基五件套

### 3.1 Tool 层

每个工具输入输出稳定，不把策略写进工具内部。工具分两层：

- **Primitive tools**：BM25、向量、取论文、簇排序、过滤、重排、校验等原子能力；
- **Macro skills**：`paper_search`、`cluster_search`、`compare_sides` 等由 primitive 组合出的技能。

宏动作可以给 agent 训练初期使用，但必须在 Trace 中展开成 primitive 调用，不能是黑箱。

当前可复用的实现入口：

- `hotspot/retrieval/hybrid.py::retrieve`
- `hotspot/subcluster.py::subcluster_adaptive`
- `hotspot/reasoning/evidence.py::evaluate`
- `hotspot/reasoning/verify.py::verify_claims`

### 3.2 State 层

统一定义内部 `RetrievalState`，至少包含：

- 原始问题与 `QueryPlan`；
- 当前候选论文/簇及分数；
- 已选证据和引用 ID；
- 已用轮数、剩余预算；
- 对话历史与 `citation_ids`；
- 已执行动作和上一步 observation。

State 是策略的输入，不是 prompt 的附属品。

### 3.3 Action 层

动作分两层，既保留细粒度，又避免动作空间爆炸。

#### Primitive tools

原子工具应满足：输入输出明确、可组合、可观测、有前置/后置条件、成本可估。

```text
bm25_search(query, k, filters)
vector_search(query_vec, k, filters)
fetch_papers(ids)
fetch_cluster_members(cluster_id)
cluster_rank(query_vec, k)
filter_metadata(ids, years, venues)
rerank(query, ids)
verify_claim(claim, evidence)
```

#### Macro skills

宏动作是 agent 训练初期的主要动作空间：

```text
paper_search       = bm25 + vector + RRF + MMR
cluster_then_drill = cluster_rank + fetch_cluster_members + fetch_papers
compare_sides      = 两次 paper_search + 证据对齐
expand_and_retry   = expand_terms + paper_search
stop_answer
refuse_or_clarify
```

宏动作必须在 Trace 中记录展开后的 primitive 调用；需要细致工作时，agent 可以下钻到 primitive。

无效动作必须 mask，例如对比问题只有一侧证据时，不能直接进入“回答”。

不要追求“最小 API”。过度原子化会导致动作空间爆炸、训练数据需求上升、credit assignment 变难、每问动作数和延迟增加。

### 3.4 Observation / Trace 层

每次请求追加一条机器可读 Trace，建议落到 `workspace/ledger/retrieval_trace.jsonl`（数据产物，不提交）。

最小字段：

```text
request_id / question / source / mode
plan
actions[]: name / level / params / observation / elapsed / tool_version
macro_expansion[]
prompt_versions / model / config_hash
outcome: route / verdicts / latency / cost / warnings
```

Trace 不是普通日志：

- 普通日志说明“发生了什么”；
- Trace 记录“当时有什么状态、有哪些动作可选、选了什么、结果如何”，可回放、可比较策略。

不记录 API key、完整摘要正文和敏感信息；候选只记 ID、分数、截断片段或哈希。

当前已有 partial trace：

- `AskResponse.meta` 中的 `plan / retrieval / evidence / decision`；
- `usage.stages` 中的阶段起止。

下一步是把它们扩展成统一、append-only、带版本的 Trace。

### 3.5 Evaluation 层

按问题类型分开评估，不能用平均分掩盖某一类失败：

- `trend`：热点/趋势；
- `fact`：具体论文事实；
- `compare`：A/B 对比；
- `relation`：主题关系；
- `newfield`：新领域；
- `out_of_scope`：超范围；
- `followup`：追问。

每类至少看：

- 检索召回/覆盖率；
- 引用支撑率；
- 幻觉率；
- 拒答正确率；
- 延迟与成本；
- 动作数 / LLM 调用数。

### 3.6 工具契约与版本化

工具实现会持续优化，不能把“地基”误解成“冻结所有实现”。正确原则是：

> **冻结接口和观测契约，不冻结实现。**

**2026-10-22 修正：harness 不是起点，而是工具成熟后的认证与暴露层。**
当前 `subcluster_adaptive` 等入口仍把检索、覆盖选择、聚类和证据门耦合在固定
流水线里；直接包装成 `ToolSpec` 会把临时策略误标成稳定工具。因此先做成熟度
验收，通过的内部 adapter 才允许注册。

工具成熟度门槛：

| 门槛 | 要求 | 不合格例子 |
|---|---|---|
| 隔离性 | 能脱离 `answer_mode` 和下游生成独立调用 | 工具内部偷偷决定 final answer |
| 契约 | 输入、输出、错误、空结果、超时均有稳定语义 | 失败返回不同形状的 dict |
| 正确性 | 有独立 golden tests | 只看最终问答是否碰巧答对 |
| 质量 | 有分类型离线指标和人工抽样 | 靠 70 题逐题调规则 |
| 性能 | 可测延迟、成本、候选规模 | 单题都跑数分钟后才给结果 |
| 可重复性 | 确定性工具固定；非确定性工具明确缓存/采样语义 | 同一输入悄悄依赖全局状态 |
| 版本语义 | 候选集、分数或参数语义变化可识别 | 改实现不记录版本 |

首批工具级验收至少覆盖：

| 工具 | 最低验收信号 |
|---|---|
| `paper_search` | Recall@K、query coverage、候选数、延迟 |
| 全局覆盖/簇工具 | 全库归属率、最近质心比例、簇规模分布、Top 簇人工可读性 |
| `evidence_gate` | 域内可答、域外拒答、可答但证据不足、泛词误放行 |
| `verify_claims` | 四态分别统计，不合并 `supported/unsupported/missing_id/no_citation` |
| `fetch_*` | 空 ID、缺失论文、批量取回、权限/数据源失败 |

阈值先由 baseline 实测后冻结，不在小样本上逐题调整。未通过的工具只保留为私有
adapter，不允许 Controller/agent 调用，也不计入策略训练轨迹。

每个工具应有 `ToolSpec`：

```text
name / version / level(primitive|macro)
args_schema / returns_schema
preconditions / postconditions
cost_model / deterministic / fallback
owner
```

Tool 输出应归一化，policy 不直接依赖某个实现的原始分数：

```text
ids / ranks / normalized_scores / counts / flags
```

变化分三类处理：

| 变化类型 | 例子 | 对 policy 的影响 | 处理 |
|---|---|---|---|
| 实现优化 | 更快的 BM25、更好的索引、更稳的 reranker | 通常很小 | 保持接口，归一化输出，直接替换 |
| 参数/默认值变化 | top_k、RRF 权重、MMR lambda | 中等 | 版本化，离线回放评估 |
| 语义/接口变化 | 分数含义变了、候选集定义变了、新增/删除动作 | 大 | 升版本，重训或加适配层 |

升级流程：

```text
离线回放旧 Trace
  → 新工具影子运行
  → 比较召回/证据/答案/延迟
  → 小流量 canary
  → 决定是否重训 policy
```

具体约束：

- 工具注册表按 `name:version` 管理，旧版本保留可调用；
- Trace 必须记录 `tool_version`；
- 如果只是实现变快、输出分布没变，通常不用重训；
- 如果候选集或分数语义变了，必须重训或加兼容适配层；
- 训练 policy 时可以随机使用多个工具版本，让策略对工具差异鲁棒；
- 工具级评测（召回/覆盖/延迟）和策略级评测（引用支撑/拒答/动作数）分开做。

### 3.7 两种工具调用方式与迁移

先澄清：这里的“专用 agent”是训练出的 policy/controller，**不是另一个通用 LLM**。它只负责检索控制：选工具、传参数、决定扩展/停止；最终答案仍由生成模型完成。

#### A. LLM 直接调工具

LLM 同时承担控制与表达：

```text
LLM 看问题 + 工具 schema
  → 选择工具和参数
  → 读 observation
  → 决定下一步
  → 生成最终答案
```

优点是冷启动快、对开放问题灵活；缺点是每步都可能一次 LLM 往返，动作多时容易选错、重复调用、忘记停止，行为受 prompt 和采样影响。

#### B. 专用 agent 间接调工具

专用 agent 接管控制回路，LLM 只做最终回答或歧义兜底：

```text
LLM / 规则生成 QueryPlan
  → 专用 agent 读取 state
  → 选择工具、参数、停止条件
  → 工具返回 observation
  → 专用 agent 继续或停止
  → LLM 生成最终答案
```

优点是动作选择稳定、延迟可控、容易做 action mask 和预算控制；缺点是需要轨迹数据，分布外问题容易僵化，工具语义变化时要版本化并可能重训。

| 维度 | A. LLM 直接调工具 | B. 专用 agent 间接调工具 |
|---|---|---|
| 控制权 | LLM 每一步决定 | 训练出的 policy 决定 |
| 动作粒度 | 工具一多容易退化，通常只适合少量宏工具 | 可用结构化状态 + action mask 管更多原子动作 |
| 延迟 | 每步可能一次 LLM 往返 | policy 决策通常毫秒级，LLM 主要只在最终回答 |
| 一致性 | 受 prompt/采样影响，波动较大 | 行为稳定，方便 A/B |
| OOD 能力 | 更强，可临场组合 | 较弱，依赖训练分布 |
| 数据需求 | 低，冷启动快 | 高，需要 Trace 和评测 |
| 可观测性 | 决策链在自然语言里，难归因 | 状态、动作、参数、observation 显式 |
| 工具升级 | 改 prompt/schema 适配 | 接口要稳定；语义变了要版本化/重训 |
| 适合场景 | 原型、开放问题、低数据 | 高频、固定任务、细致动作、严格预算 |

结论：

- 如果目标是“充分细致的工作”，B 更适合，因为 LLM 直接面对大量原子工具时 tool selection 会退化；
- 但 B 也保留 macro skills 作为训练初期的动作空间，需要时再下钻到 primitive；
- 工具成熟前，当前固定流水线只作 provisional baseline，不把其阶段日志冒充工具 Trace；
- 工具成熟并通过 `ToolSpec` 校验后，先用 A 做冷启动 baseline 并记录完整 action Trace；
- 最终形态是 B 主导检索控制，LLM 负责最终回答、歧义/OOD 兜底和必要校验。

#### 迁移方式

A 和 B 共用同一套工具，不各写一套：

```text
                共用 ToolSpec / Registry
                  ↑                 ↑
        A: LLM controller    B: 专用 agent controller
                  ↘                 ↙
              Evidence Gate → Answer → Verify
```

迁移步骤：

1. 冻结当前 heuristic 流水线，记录 provisional baseline；
2. 逐个抽取工具，完成隔离性、golden tests、分类型质量和性能验收；
3. 只把通过的工具有 `ToolSpec` + registry，宏动作展开为 primitive；
4. 让 A 在成熟工具上调工具，状态机限制扩展/repair 次数并记录 action Trace；
5. 用 A 的 Trace 训练 B 的行为克隆 baseline；
6. 用旧 Trace 离线回放，按 query 类型比较 A 与 B；
7. 先在小流量上让 B 接管高置信、常见类型，A 保留为 fallback；
8. 每次切换记录 `controller_version` 和 `tool_version`，可以回滚；
9. 只有在引用支撑、拒答、延迟/成本不退化时，才扩大 B 的比例。

切换门槛不能看总分，要看分类型：

- B 在哪些 query 类型上稳定优于 A；
- B 的 OOD/低置信情况是否能正确升级给 A；
- 工具版本变化后，B 是否仍能工作；
- 回滚是否只需切 controller，不动工具和对外契约。

## 4. 检索地基

理想检索流程只记原则，不展开具体模型：

1. **Scope / Plan**：判断是否本库问题，生成 `QueryPlan`；
2. **Candidate Recall**：BM25 + dense + cluster + metadata；
3. **Fusion / Rerank**：融合、重排、多样性；
4. **Coarse-to-Fine**：热点走 cluster-first，事实走 paper-first，比较走两侧，关系走 graph，追问走 history；
5. **Evidence Gate**：证据够不够；不够才允许一次扩展；
6. **Answer / Verify**：规则先查 ID 和引用，模糊 claim 再交给模型；
7. **Trace**：记录每一步的候选和决策。

问题形态与证据要求：

| 问题形态 | 首检索 | 必要证据 | 不足时 |
|---|---|---|---|
| 热点/趋势 | 簇/卡片 | ≥2 个可比簇 + 跨会计数 | 扩展一次或改措辞 |
| 具体事实 | 论文 | 1–3 篇摘要 | 同义词扩展一次 |
| 比较型 | 两边各自的簇/论文 | 两边都要有证据 | 缺一边就澄清/拒答 |
| 关系型 | co-cite / MPS | 路径或共同来源 | 明确说图数据不可用 |
| 新领域 | 新进簇 | 年份/会议 + 新进状态 | 扩展或拒答 |
| 超范围 | scope 检查 | 无 | 直接拒答 |
| 追问 | 历史 + citation_ids | 前文论文 | 不重新检索 |

红线：`铺开 / 新进 / 单会` 必须由 `spread_state` 从计数计算，不能由答案 LLM 推断。

## 5. 数据地基

- 修全局聚类覆盖：当前全库聚类噪声率过高，先保证论文有可用的粗粒度归属；
- 在线局部细化继续保留，但建立在覆盖可用的全局索引上；
- `spread_state` 显式计算并进入证据；
- 向量/BM25 索引常驻或缓存，避免每次请求重建；
- 先保证工具质量，再谈学习策略。

## 6. 演进顺序

### 阶段 1：Trace（不改行为）

- 先记录当前固定流水线的 `plan → stages → outcome`，标为 provisional baseline；
- 完成工具化后改为真正的 `plan → actions → observation → outcome`，并展开 macro → primitive；
- 记录 prompt/config/model 版本；
- 记录 `tool_version` 和归一化 observation；
- 工具未成熟前不启动 LLM 直接调工具，不把固定阶段日志用于策略训练；
- 验收：100% 请求有 Trace；成熟工具版本下能按 `request_id` 回放 action。

### 阶段 2：L2 覆盖

- 全局粗聚类 + 在线局部细化；
- 补 `spread_state` 和覆盖率统计；
- 验收：覆盖率达到可解释区间，Top 主题人工可读；具体阈值实测后定。

### 阶段 3：工具成熟与边界

- 建工具成熟度矩阵：隔离性、契约、正确性、质量、性能、失败行为、版本语义；
- 先审计全库 L2 覆盖，再分别建立 `paper_search`、簇工具、`evidence_gate`、
  `verify_claims` 的离线基准；
- 采用绞杀者方式从 `subcluster_adaptive` 逐个拆出候选过滤、粗簇选择、局部聚类、
  证据门，不做一次性大重构；
- 先跑通最小纵链 `paper_search → evidence_gate → fetch_papers`；
- 未通过工具只做私有 adapter，不注册、不暴露给 Controller/agent；
- 验收：工具可独立调用；同输入稳定或明确非确定性；失败返回结构化 observation；
  工具级指标达到 baseline 冻结阈值。

### 阶段 4：显式 Controller

- 把当前 heuristic 包装成 baseline policy；
- 只允许 Controller 调用阶段 3 已通过的工具；
- 冻结 v1 `ToolSpec` / registry，宏动作只通过注册表调用并展开 primitive；
- 在 Trace 中保留宏动作展开和工具版本；
- 不改既有对外契约；
- 验收：在现有评测集上行为与当前 baseline 对齐，再谈替换。

### 阶段 5：证据与校验

- MMR/覆盖度，热点问题至少覆盖多个簇；
- 比较型 claim 必须有比较证据；
- verify 批量/并行，减少串行 LLM 调用；
- 验收：引用支撑率、拒答正确率、延迟同时可测。

### 阶段 6：策略数据

- 积累 200–500 条 Trace；
- 做错误归因和分类型评测；
- 再决定是否训练策略模型；
- 学习型策略没有稳定超过 heuristic，就保留 heuristic。

### 阶段 7：专用 agent 接管

- 用阶段 1–6 的成熟工具 Trace 训练专用 agent/controller；
- A（LLM 直接调工具）保留为 baseline 和 OOD fallback；
- 按 query 类型逐步切换，不做一次性全量替换；
- 每次切换记录 `controller_version` / `tool_version`，支持回滚；
- 验收：分类型指标不退化，OOD 能升级给 A，工具升级后仍可工作。

## 7. 技术选型后置

本文不记录具体网络架构、参数量和训练超参。后续单独开“策略模型选型”文档，选型标准至少包括：

- 数据量是否足够；
- 推理延迟是否可控；
- 是否可解释、可回放；
- 是否能离线评测；
- 是否真的优于 heuristic baseline。

可选形态包括小型策略模型、学习型 reranker，或暂时不训练模型；由阶段 1–6 的数据决定。

## 8. 明确不做

- 不继续把加同义词/query 规则作为主方向；
- 不做多智能体 swarm；
- 不做端到端 RL 从零训练；
- 不在小数据上训大模型；
- 不让 LLM 决定三态或机械校验；
- 不改变对外接口语义，新增字段只做 additive。

## 9. 性能预算

这里只记约束，不记具体模型性能：

- 非 LLM 检索/控制器开销控制在百毫秒级；
- 每问 LLM 调用目标 3–4 次以内；
- 意图路径要有最大扩展轮数和最大 repair 次数；
- Trace 本身不能显著增加请求延迟；
- 端到端目标在真实端点 benchmark 后确定并写入评测文档。
