# 前端与算法改造路线

> 2026-10-20 记录。长期参考：前半部分是把 `hotspot.api` 从“单用户问答接口”扩展到“研究组群助手”的职责/契约设计，后半部分是双人并行开发步骤。
> **本文不是 API v1 契约本身**；正式契约仍以 `规划/接口契约-前端与算法.md` 为准。后端实现 `scope`/`meta.plan` 后，再统一升 v2 并回写该契约。

| 事项 | 决定 |

| 当前 g05 停用词补丁 | **临时修复**，最终由结构化 `scope` 取代 |

## 1. 要解决的问题

### 1.1 查询约束被当成文本词

当前 `parse_query` 主要输出 `topic_en / keywords / years / intent`，没有区分：

- 回答必须围绕的核心主题；
- 用于召回的扩展词；
- 年份、会议、数据源等硬约束；
- 答案必须覆盖的方法/数据集/指标等软要求。

结果是“近两年”进入文本后又被停用词处理：既可能丢失时间约束，也可能因 `popular/two/years` 等泛化词压低 coverage。g05 的误拒就是这条链路的直接证据。

### 1.2 coverage 门控承担了过多职责

coverage 只应判断“top 候选是否覆盖核心主题”，不应同时负责：

- 时间过滤；
- 同义词扩展；
- 会议/数据源权限；
- 论文类型筛选；
- 群聊触发。

### 1.3 群助手不能复用同步单用户链路

微信群消息需要触发判断、线程解析、多人身份、权限、异步回复、消息分片和合规接入；这些都不应进入 `Engine.ask`。

## 2. 目标与边界

- `hotspot.api.Engine` 保持**无状态**；
- `AskRequest` 只承载一次研究问答所需的输入；
- 群 ID、用户 ID、消息 ID、回复目标、微信消息类型不进入 Engine；
- 算法返回结构化 `Answer`/`topics`/`citations`/`warnings`/`meta`，前端负责渲染和投递；
- 时间约束必须显式保留，不得静默回退到其他年份。

## 3. 查询规划三层结构

```text
semantic
  input_class / intent / core_terms / keywords /
  scope / requirements / confidence

conversation
  group_id / actor_id / message_id / reply_to /
  addressing / resolved_question / recent_turns

delivery
  audience / mode / mention_actor / max_chars / format
```

### 3.1 semantic

| 字段 | 用途 |
|---|---|
| `input_class` | valid / nonsense / out_of_scope / injection / unsafe / ambiguous / chitchat / spam / duplicate / unsupported_media / multi_question |
| `intent` | trend / fact / compare / relation / worth / newfield / followup / meta / help / digest / paper_link / group_memory / admin |
| `core_terms` | 回答主题和 coverage 门控的唯一依据 |
| `keywords` | BM25/向量召回的同义扩展，不参与 coverage |
| `scope` | 前端解析的硬过滤条件 |
| `requirements` | 必须比较、必须覆盖方法/数据集/指标等软要求 |
| `confidence` | 规划置信度；低置信度进入澄清或拒答策略 |

### 3.2 conversation

由前端/网关维护：群、用户、消息、线程、@/回复关系、指代解析结果。Engine 只消费归一化后的 `history`。

### 3.3 delivery

由前端决定：群/私聊、简短/完整/线程、是否 @ 提问人、消息长度、文本/卡片格式。

## 4. scope 的归属

**前端解析 scope，后端校验并应用。**

```json
{
  "scope": {
    "years": [2024, 2025],
    "years_explicit": true,
    "venues": ["ICLR", "ICML"],
    "sources": ["meeting"],
    "subfields": [],
    "paper_types": []
  }
}
```

规则：

1. 前端传来的 `scope` 是权威来源；
2. 后端只做合法性校验、年份/会议过滤和回显；
3. `years_explicit=false` 表示用户没指定年份，不能自动补成某一年；
4. 用户明确指定年份时，范围内无证据就明确拒答/说明，不回退到其他年份；
5. 直接调用 API/脚本且没传 `scope` 时，不做年份过滤；不得偷偷使用默认年份；
6. `scope` 不进入 `core_terms`，也不参与 BM25 词项。

## 5. 前端 / 算法职责

| 工作 | 算法 | 前端/网关 |
|---|---|---|
| `core_terms` / `keywords` / `intent` / `input_class` | ✅ | — |
| `scope` 解析 | — | ✅ |
| `scope` 校验、年份/会议过滤 | ✅ | 传显式 scope |
| BM25 / dense / RRF / rerank / MMR | ✅ | — |
| coverage 门控 | ✅ | — |
| answer / citation / verify | ✅ | — |
| 群触发、@、线程、群/用户上下文 | — | ✅ |
| 账号、权限、配额、API key | — | ✅ |
| 异步队列、幂等、消息分片 | — | ✅ |
| 微信/企业微信协议、验签、合规 | — | ✅ |
| 周报订阅/定时推送 | 生成能力 | 调度与投递 |
| PDF/图片/语音/链接工具 | — | 工具路由 |

## 6. 算法改造步骤

1. `parse_query` 增加 `core_terms`，保留 `topic_en/keywords/years/intent` 兼容字段；
2. 增加 `input_class`、`confidence` 和 `scope` 的消费/校验；
3. coverage 只使用 `core_terms`；停用词仅作为旧输入 fallback；
4. 年份/会议从文本词移出，按 scope 在候选层过滤；
5. 保持 BM25 + dense + RRF + 可选 rerank/MMR；
6. 为 `compare`、`out_of_scope`、`nonsense`、`injection` 设计独立策略；
7. `AskResponse.meta.plan` 返回规划结果，`meta.retrieval` 返回候选/coverage 统计；
8. 评测逐题增量落盘，避免中断丢失；补 g05、2025、近两年、无年份、超范围、A/B、胡言乱语回归。

## 7. 前端/网关改造步骤

1. 企业微信/公众号回调、验签、去重；
2. 触发策略：直接 @、回复机器人、命令、管理员关键词；
3. 群/用户/消息/线程上下文与指代解析；
4. 异步队列：快速 ack → worker → 出站回复；
5. MySQL/Redis：群配置、用户、消息、会话、订阅、配额、幂等键；
6. 结果渲染、引用链接、长消息分片、@提问人；
7. 周报订阅、定时推送、静默时段、管理员开关；
8. 链接/PDF/图片/语音工具路由；
9. 群级 key、预算、限流、审计和脱敏。

## 8. 双人并行开发

### Sprint 0：先冻结 draft schema

两人一起完成，最多半天：

- `scope` 字段名/类型/示例；
- `meta.plan` 字段名；
- `AskRequest` 是否接受可选 `scope`；
- 错误/拒答/澄清的 interim 语义；
- 建立 `StubEngine` 和请求/响应 fixture。

这一步是唯一的强前置；不冻结字段名，两边会各写一套。

### Sprint 1：双轨并行

| 算法开发者 | 前端开发者 |
|---|---|
| planner：core_terms/intent/input_class | `scope` 解析器 |
| scope 校验 + 年份/会议过滤 | 群网关、触发、线程 |
| hybrid 检索与 coverage | MySQL/Redis 表结构 |
| 算法 fixture 与单元测试 | 异步 ack/worker、消息分片 |

前端用 `StubEngine` 测网关；算法用 fixture 测过滤和门控。两边不需要等待对方完成。

### Sprint 2：实现汇合

| 算法开发者 | 前端开发者 |
|---|---|
| answer/verify、compare/out_of_scope/nonsense | 接真实 `Engine` 适配器 |
| 批量校验、阶段耗时 | 渲染/引用/群消息投递 |
| 跑 g05、年份、无年份、超范围回归 | 群/用户/权限/配额联调 |

后端实现完成后，再更新 `规划/接口契约-前端与算法.md` 并升 v2；在此之前前端按 draft schema 开发。

### Sprint 3：扩展能力

- 算法：ranking/clustering、完整 G0/G1、跨会评测；
- 前端：周报、微信正式接入、链接/PDF/语音工具；
- 共同：压测、审计、限流和失败恢复。

## 9. 契约演进

### 可安全增加（v1 兼容）

- `AskResponse.meta.plan`：`input_class/intent/core_terms/scope/requirements/confidence`；
- `AskResponse.meta.retrieval`：候选数、coverage、answerable；
- `AskRequest` 的可选 `scope`（后端实现后）。

### 不建议放入 `AskRequest`

- `group_id`、`actor_id`、`message_id`、`reply_to`；
- 微信消息类型、媒体 URL；
- 群成员权限；
- 投递方式。

### 需要 v2 的变化

- 给 `route` 增加 `clarify` / `reject`；
- 改变 `answer` 结构；
- 把 `plan` 设为必填；
- 把群状态、媒体工具或异步任务塞进 `ask`。

**v2 文档等后端实现对应字段后再改；当前只记录本文。**

## 10. 验收用例

- g05 不再因 `popular/large/two/years` 被误拒；
- “近两年”回答明确写出实际年份范围；
- “2025”只使用 2025，不静默跨年；
- 无年份问题不被默认年份过滤；
- `quantum computing for cats` 之类超范围问题拒答；
- nonsense / injection 在检索前被拦截；
- A/B compare 缺一侧时明确说明缺失；
- 群消息 5 秒内 ack，同一 `message_id` 不重复回答；
- 前端引用链接、长消息分片、@提问人正常；
- `check_api.py`、`check_tree.py` 全绿。
