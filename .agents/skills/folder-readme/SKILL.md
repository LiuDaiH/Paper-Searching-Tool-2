# 索引树维护（folder-readme）

给当前项目维护一棵「从根 README 出发就能读全」的索引树。不是"文档写得好"，是对三个具体失败模式的回答：**静默腐化**（清单落后于磁盘、没人报警）、**入口缺失**（新会话不知道从哪进）、**靠人记住的约定失效**。

## 一、这棵树的形状

三层，节点只有两种类型；**子 README 之间必须同构，根必须不同构**（根是地图，不含状态、不含叶子细节）。

```
根 README.md          ← 总目录。回答"有哪些块"
  ├── 子 README.md    ← 每块一份。回答"这块有什么、现在到哪了"
  │     └── 叶子文件   ← 见下方「计划文件 / 数据文件」两类
  └── 根目录散件       ← 不属任何块的文件，也在根 README 里登记
```

### 叶子文件分两类：计划文件 / 数据文件

**任何 md（和文件）先归到两类之一，README 按这个分，浏览也按这个读。**

| 类型 | 是什么 | 谁来读 | 例子 |
|---|---|---|---|
| **计划文件** | 记录**日志、经验、规划**、决策、状态的文件 | **新会话必须读**，浏览项目只读这一类 | `日志/`、`经验/`、`规划/`、设计文档、`_index.md`、README |
| **数据文件** | 语料、产物、生成数据、构建结果——量大、可重建 | **新会话不读**（占 token 且失真） | 向量 `.npz`、聚类 json、数据集、缓存 |

> **每次浏览项目只读计划文件。** 数据文件不进上下文：它们要么能重建、要么本该由脚本/工具读，人读只会灌 token 又被过大文件带偏。

⚠️ **命名**：子 README 不要也叫 `README.md`——同一个项目里所有 README 同名会造成双链歧义。复刻时子 README 叫 `_index.md` 或 `README-<folder>.md`。

⚠️ **「直辖」文件夹**：没有子 README 的文件夹（如 `日志/`），由根 README 直接管辖——根里给它一个专属节，并**明确写**"没有子 README"。否则新会话会去找它。

## 二、单一索引原则

> **同一个事实只留一份，留在最不容易腐的那一层。**

判据：**问"这个数变了的时候，谁会知道？"** 如果答案是"没人"，就把它挪到唯一的那一处。典型：

| 数字 | 该放哪 |
|---|---|
| 一个文件夹下有多少**计划文件** | **那个文件夹的 README §3**，或根里管辖它的那节 |
| 一个文件夹下有多少**数据文件** | **不逐条列**——只在 §3 记为"数据 ×N，可重建"，别把几千个产物读进索引 |
| 全库总篇数 / 外部源可用性 | **只写一处**，别处只引用 |
| 改了多少、这次做了什么 | **哪里都不放**（根是地图，不是流水账） |

## 三、你改了什么 → 该写哪里（本 skill 的核心，先做再报告）

**规则：改动任何 md 之后，顺着树往上写，终点是根 README。由执行这次改动的那次会话写。**

| 你改了什么 | 子 README | 根 README |
|---|---|---|
| 新建一个**计划文件** | §3 加一行 | 只改 §1 那一行的「最后更新」 |
| 删除 / 改名一个计划文件 | §3 删行 / 改行 | 同上 |
| 数据文件生成 / 体积变大 | **不动**（§3 那个"数据 ×N"一般不逐条登记） | 不动 |
| 新建/删除/改名一个 `.py` | 「脚本速查」加/删/改一行 | 只跑自检 |
| 改了工作状态、判据 | §2 改 | **不动** |
| 文件夹的**用途定位变了** | §1 改 | 改 §1 那一行的「干什么」 |
| 新建一篇日志 | — | 根里那一节加一行 |
| 根目录新建 / 删除散件 | — | §3 加 / 删一行 |
| 只改错别字、只动排版 | **不动** | **不动** |

> **根只吃「那一行」。它是地图，不是流水账。** 一旦开始记"这次改了什么"，根就会变成那种"会让人重做已经做完的事"的失真清单。
> **期望会被跳过，步骤不会**——把回写写成本 skill 硬要求、挂在"报告"这个必然动作前面。

## 四、自检脚本

树的失败模式是**静默**——没有东西会报错，它只是慢慢变得不全。所以自检必须**离线、秒级、确定性**，且查三件事：

1. **悬空双链 = 0**（`[[X]]` 指向不存在的文件）
2. **无孤儿 md**（每个文档都能从根走到 ← 承诺的本体；**只查悬空不查孤儿 = 假绿**）
3. **README 覆盖**（每个含 md 的一级文件夹都有 README）
4. **脚本速查一致**（每个含 `.py` 的目录，其 README「脚本速查」与磁盘 `.py` **双向**一致：缺登记报、冗余报）

⚠️ 跑起来第一件事通常是给 `data_rules` 加条目——把**数据**（语料、缓存、构建产物、skill 模板）划出去，剩下的才是真的孤儿。**先跑，再按报告修配置，别按想象修配置。**

skill 与模板通常**不在树上**（声明进根 README §5「不在树上的目录」，并在自检里豁免）。

## 五、README 模板

**根 README**（五节，`tags: [索引, 说明书]`）：

```markdown
# <项目名> · 总目录
## 1. 索引树          ← 表格：文件夹/干什么/它的README/最后更新
## 2. <直辖文件夹的索引>  ← 没有子 README 的文件夹
## 3. 根目录的散件
## 4. 建议阅读顺序       ← 决定新会话的头五分钟；**只列计划文件，不列数据**
## 5. 不在树上的目录      ← 每项写"为什么不列"
## 6. 维护本文件（树形回写） ← §三的传播表，本文件那一列
```

**子 README**（同构，`_index.md`）：

```markdown
## 1. 这个文件夹是什么
## 2. 当前工作状态      ← 问"现在到哪了"只读这一节
## 3. 文件清单          ← 分两段：**计划文件**（逐条列，且是唯一要读的）
                        ←          **数据文件**（记为"数据 ×N，可重建，不读"）
## 4. 建议阅读顺序       ← **只列计划文件**——新会话按这个读
## 5. 相关              ← 含上位指针（指回根，用纯文本路径）
```

⚠️ §3 与 §4 是配套的：**§3 标出"哪些是计划文件"，§4 就只排它们**。数据文件不出现 §4——否则"浏览只读计划文件"成了一句空话，又被几千个产物拖回原点。

## 脚本速查（README 记录其直接目录的脚本）

每个 README 记录它**直接管辖的那一层目录**下的 `.py`，每条 = `文件名` + 一句功能
（取自该脚本的 **docstring 首句**，单一源，README 不另写全文）。

| 项 | 规则 |
|---|---|
| 谁登记 | 每个含直接 `.py` 的目录的 README（文件名用 `_index.md` / `README.md`） |
| 记什么 | `- \`file.py\` —— 一句`（docstring 首句） |
| 不记 | `__init__.py`（包脚手架）；子目录的 `.py` 由**子目录自己**的 README 管 |
| 防腐化 | 新增/删除/改名 `.py` → 更新对应 README；自检脚本（§四第 4 条）核对双向一致 |

示例（某目录 `_index.md` 的「脚本速查」节）：

```markdown
## 脚本速查
- `foo.py` —— L2 把 X 变成 Y。
- `bar.py` —— 校验 Z。
```

> 这条清单是**派生物**，最易腐——所以必须交给自检核对，而不是靠"记得改"。

## 六、入口那一句话（最容易漏，漏了全废）

树是给"新会话"用的，而**新会话不会自己去找树**。项目根必须有 `CLAUDE.md` / `AGENTS.md` / `.cursorrules`，至少四条：

1. **一张表**：有哪几块、各自是什么、哪块可写哪块只读
2. **一句硬要求**：「动手前先读那个文件夹的 README」
3. **一句回写要求**：「改动之后回写，并向上传播到根」
4. **撞车警告**（仅当同名时）

> **硬规则：浏览项目只读计划文件。** 入口表把每块标成「计划 / 数据」；读 README、日志、规划、经验这类**计划文件**进上下文，向量/聚类产物/语料这类**数据文件**不读（要么可重建，要么该由脚本读）。少了第 1、2 条，树是装饰品；**不区分计划/数据，浏览就被数据文件灌满。**

## 七、维护这份 skill

- 想调「回写表」→ 改 **§三** 那张表
- 想调自检的四项检查 → 改 **§四**
- 想调 README 模板 → 改 **§五**，模板里「计划 / 数据」两份清单是一对，不要拆开
- 想调「浏览只读计划文件」的判定（什么算计划文件）→ 改 **§一** 那张两分表
- 想调「脚本速查」规则（谁登记/记什么）→ 改「脚本速查」那一节
- 改了表格要和它的说明文字连着读一遍（一对，不要插进中间），比看 diff 可靠
